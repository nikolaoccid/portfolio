We planned a database migration. A 10,000-step test project showed we didn't need one.

Large projects in our offline-first React Native app were slow, and the plan was to move local storage to SQLite. Before starting, I wanted to know whether storage was the bottleneck.

Measuring

I built a synthetic project that scales from 100 to 10,000 steps, and a harness that runs the real download, store and tap code against it with storage mocked by a plain Map. That removes storage cost, so what remains is pure JavaScript work, the part a storage swap would not touch. The numbers come from Node, not a phone, so the scaling is the result, not the milliseconds.

What it showed

Two problems, neither in storage:

  1. One tap cost 1 + tasks + 6 store reads, because completion counts were recomputed by reading every task's criteria and deep-cloning the project. At 500 tasks that was 507 reads and a 141 KB rewrite per tap.
  2. Writes made during a download were change-tracked: five undo records per step, 50,000 at 10,000 steps, held in memory until the next user action absorbed them. That is a correctness bug, not only a cost: removing that action from the offline queue could have undone a download.

Opening a task was already about 0 ms and under 15 KB at any project size, so the data model was fine.

Options

Migrate to SQLite, or fix the two algorithms behind the existing storage interface. The SQLite library we had linked had no working driver and hung on a 10,000-row batch in the test, so it would have added risk without removing either problem. I chose the second.

Result

A tap now reads only the task that changed and derives the totals in memory: 8 store reads at every project size, down from 507. Leaked change records after a download: 0. Downloads were 8 to 14% faster. A characterization test showed every stored key and value unchanged; only the read count moved.
